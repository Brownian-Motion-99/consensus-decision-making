# 台灣版「答案一致」派對遊戲：Demo 架構與產品設計

## Context
目標是做一個台灣版的「全員答案一致」派對遊戲（玩法參考《一致するまで終われまテン》，名稱、美術、文案、題庫全部自行設計）。正式上線一個人做不完，所以先做 demo：**同一區域網路內的多台裝置同時連線遊玩**。
本文件只談產品設計和架構方向。**要等使用者說「實作程式碼」才開始寫程式。**

## 已確定的設計決策
| 項目 | 決定 |
|---|---|
| 作答方式 | 在白板上手寫（手指、觸控筆、滑鼠都可以），送出後是一張 PNG 圖片 |
| 人數 | 每間房 2–8 人，列席人員也算在 8 人裡面。遊戲中途可以加入，見「中途加入、休會與房間回收」 |
| 一致判定 | 全部由主持人判定，系統不自動比對 |
| 主持人 | 由其中一位玩家兼任，也要作答 |
| 沒有一致時 | 記錄這題沒有一致，繼續出下一題，直到達成目標為止 |
| 結束條件 | 主持人在開局前設定「一致幾次才結束」（主持人自由輸入 1–99 次，預設 3 次）。題數沒有上限，題庫用完會重新洗牌 |
| 不做 | 認人（帳號、斷線後恢復原本的身分）、大型題庫、投稿。沒有個人計分，所以重新整理後以新人的身分重新加入就好 |
| 技術方向 | Node.js server ＋ WebSocket ＋ 網頁前端（不用安裝 App） |

## 威脅模型

決定「多壞才算壞」，實作和審查都以這裡為準。

- **對手**：只有一起玩的朋友，偶爾手賤亂按、亂取暱稱。沒有公開房間，也還沒有正式上線的計畫，所以不考慮陌生人、手上有很多 IP 的人，或刻意要打垮 server 的人。
- **一定不能發生**：
  - **正常使用時 server 掛掉。** 包括網路慢、手機鎖螢幕、重新整理、同時按按鈕這類正常會遇到的情況。刻意構造的極端輸入不在此限，不需要為它們設計防禦。
  - **畫面暴雷。** 公開之前，任何人都看不到別人的答案（見「架構方向」）。
- **可以接受**：
  - 有人搗亂毀了自己所在的那一間房：大家離開、重開一間就好。朋友搗亂，在現場就能解決。
  - 刻意構造的輸入造成的怪現象，例如奇怪的 Unicode 暱稱，只要不讓 server 掛掉、不暴雷就好。

## 遊戲流程
1. **建房**：任何人打開首頁按「開新房間」，就會拿到一個 4 碼房號，接著取暱稱加入，開房的人就是主持人（就算有人先取好暱稱，開房的人加入時也會拿回主持人）。一台 server 可以同時有多間房（暫定上限 100 間）。
2. **加入**：大廳有「複製房號」「複製連結」按鈕，其他玩家開連結（網址帶房號），或在首頁輸入房號，進房後再取暱稱進入大廳。房間只能靠房號進入，沒有公開的房間列表。
3. **開局**：人數達到 2 人以上時，主持人按下「開始」。開局後加入的人先成為列席人員，見「中途加入、休會與房間回收」。
4. **每一題**：
   - 所有人看到同一道題目，各自在白板上手寫答案後送出。
   - 送出前看不到別人的答案，主持人也一樣，這樣才公平。答案送出後就不能修改。作答中的畫面不顯示進度；送出答案之後，主持人和一般玩家都會看到「已作答 3/5」這類進度。
   - 全員都送出後，主持人畫面會出現「公開答案」按鈕，主持人按下後才同時公開所有答案。
   - 主持人按「一致」或「不一致」做出判定。
   - 系統記錄結果，然後進入下一題。
5. **結算**：一致次數達到目標後，主持人按下「看結算」。結算畫面只顯示總共答了幾題、一致幾次，不顯示每題的答案回顧。公開答案的階段也會即時顯示目前一致幾題、不一致幾題。

## 架構方向
- **Server 是唯一的權威狀態來源**：負責房間、玩家、目前題號、各玩家答案和判定結果。Client 只負責顯示，並送出操作。
- **多房間**：每間房是一個獨立的容器（`RoomSession`＝遊戲狀態機＋這間房的連線＋廣播），server 只用房號把連線轉給對應的房間。房間什麼時候收掉，見「中途加入、休會與房間回收」。
- **狀態機**：`lobby → answering → revealed → judged → (下一題 answering | finished)`。每次狀態前進都由主持人的事件推動，包括「開始」「公開答案」「一致／不一致」。從 answering 進到 revealed 時，server 會先檢查是否全員都已送出答案，還沒送齊就拒絕「公開答案」的事件。遊戲中人數不足時，從 answering、revealed、judged 進入 `paused`，主持人按「繼續會議」後的行為和「下一題」相同。
- **WebSocket 訊息分兩類**：client 送出意圖（加入、送出答案、判定、開始），server 廣播狀態快照。答案公開前，server 不會把其他人的答案送到任何 client，連主持人的 client 也不送。
- **網路慢的連線只收最新的快照**：一條連線的上一份快照還沒送完時，server 不送新的快照，只記下「有更新」；等上一份送完，再補送一份當下最新的快照，中間的版本直接略過。每條連線同時最多只有一份快照在排隊。
- **排隊太多就斷線**：除了正在送的那一份快照，一條連線還沒送出去的訊息（錯誤、通知等）超過 1MB 時，server 直接斷掉這條連線。正在送的快照不算進去，因為一份快照最大約 1.8MB（公開答案後有 9 張圖），算進去的話，網路慢的正常玩家在公開答案時就會被斷線。被斷線的人重新整理就能回來。
- **暱稱**：一定要是字串，否則拒絕。前後的空白去掉後不能是空的，最多 100 個字（以 Unicode code point 計算，大部分 emoji 算 1 個，組合起來的 emoji 會算好幾個），超過就拒絕加入並提示。只由看不見的字元（零寬空格、韓文填充字元、點字空白等）組成的暱稱，自動換成「匿名」加上一種台灣的動物，例如「匿名水豚」「匿名石虎」。暱稱可以重複。
- **權限**：只有 host 能送出「開始」「公開答案」和判定的事件，server 會驗證身分。
- **題庫**：用一個靜態檔案存放題目，每局隨機抽 N 題。題目內容全部自己寫。
- **區網連線**：`npm run start:lan` 時 server 監聽 `0.0.0.0`，啟動時偵測本機的區網 IP，在終端機印出網址和 QR code（只用來開首頁，房間邀請改用複製房號／連結）。預設 `npm start` 只監聽 `127.0.0.1`。

## 斷線、題庫、名稱與視覺
- **主持人斷線**：server 從還在線的玩家中隨機挑一位當新主持人，並廣播給所有人。
- **任何玩家斷線**：這位玩家會從本局移除，「全員已作答」只計算還在線的玩家。如果在線的玩家少於 2 位，就進入休會，見下一節。
- **怎樣算斷線**：連線關閉，或 server 每 10 秒送一次 ping、連續 3 次沒有回應（約 30 到 40 秒）。不能太快判定，因為網路慢的玩家在收大快照（公開答案後約 1.8MB）時，回應會排在快照後面。代價是真的斷線的人要晚一點才會被移除。
- **斷線畫面**：只請玩家重新整理，不預告會變成什麼身分。重新整理後取好暱稱，依當下的階段決定：作答中、已公開、已判定時先列席，其他時候直接成為玩家（見「中途加入、休會與房間回收」）。

## 中途加入、休會與房間回收
- **隨時可以加入**：任何時候都能用會議編號進房、取暱稱加入。重新整理也是用這個方式回來，server 不會認出是同一個人。
- **加入時的身分**：
  | 加入時的階段 | 身分 |
  |---|---|
  | 大廳、休會中、結算 | 直接成為玩家 |
  | 作答中、已公開、已判定 | 列席人員 |
- **開房的人晚到**：開房的人只有在大廳取暱稱時才會拿回主持人；題目進行中才取暱稱的話，和其他人一樣先列席，也不會拿回主持人。刻意不處理，因為取好暱稱之前看不到會議編號，其他人幾乎不可能比開房的人先進房。
- **列席人員**：畫面只顯示「下個議案開始時即可進入會議」。server 不會把題目和任何答案送給列席人員。列席人員不作答、不算在「全員已作答」裡，也不會被選為主持人。
- **列席轉玩家**：下一題開始時、進入休會時、回到大廳或結算時，所有列席人員都會轉為玩家。
- **人數上限**：玩家加上列席人員最多 8 人，滿了就不能加入。
- **還沒取暱稱的連線**：輸入會議編號、但還沒取暱稱的連線，和列席人員一樣收不到題目和任何答案。每間房最多 5 條，超過的連線會被直接斷線，錯誤訊息不說明原因（正常使用不會碰到，碰到的大概是惡意連線）。
- **休會**：遊戲進行中（作答中、已公開、已判定）在線的玩家少於 2 位時，進入休會。
  - 保留目標決議數、已經判定的結果和題號；還沒判定的那一題作廢，不算進統計。
  - 目標決議數只能在大廳調整，休會中**刻意不開放修改**。想提早結束的話，大家各自離開就好。
  - 休會中加入的人直接成為玩家。玩家回到 2 位以上時，主持人畫面出現「繼續會議」。按下後的行為和「下一題」相同：已達目標就進入結算，否則出下一題。
  - 休會中所有玩家都離開的話，和現在一樣重置回大廳。
- **房間回收**：
  - 最後一條連線離開後，房間保留 30 秒才收掉。這段時間內有人用會議編號進來，房間就繼續使用（例如一個人在房間裡重新整理）。
  - 房間裡連續 10 分鐘沒有任何玩家或列席人員時（只剩還沒取暱稱的連線，或完全沒有連線），收掉房間，還連著的人回到首頁並看到提示。
- **題庫**：聯想題和意見分歧的題目，每局從中抽題。題目用開會的語氣，依照題目類型套固定句型：聯想題用「關於「夏天」，大家的第一印象為何？」，比較最好或最差的題目用「請各位表決：……」，問做法或偏好的題目用「本案討論：……」，必備物品用「請各位提案：……」，網路梗用「臨時動議：……」，縮寫用「關於「ATM」，請各位說明其定義。」
- **遊戲名稱**：「本次會議我們採取共識決」，短名稱「共識決」（主畫面圖示、空間不夠的地方用）。舊名「默契一致」已停用。
- **文案語氣**：介面用語模仿開會。本文件和程式碼仍用原本的概念名稱，畫面上的用語對照如下：

  | 概念（文件、程式碼） | 畫面用語 |
  |---|---|
  | 主持人（host） | 主席 |
  | 房間／房號 | 會議室／會議編號（開房＝召開會議） |
  | 一致／不一致 | 達成共識／未達共識 |
  | 目標一致次數 | 需要通過幾項決議 |
  | 開始遊戲 | 開始會議 |
  | 結算 | 會議紀錄（提前結束＝提前散會） |
  | 回到大廳 | 召開下一場會議 |
  | 玩家斷線 | 離席 |
  | 列席人員（observer） | 列席人員 |
  | 休會（paused） | 休會 |
- **視覺**：只做乾淨的骨架，包括基本版面、能在手機上使用，以及集中管理的 CSS 變數，方便之後微調。

## 驗證方式（實作後）
- 在同一個 Wi-Fi 下，用一台電腦當主持人，再用 2–3 支手機加入，完整玩完一局。
- 確認答案公開前任何裝置都看不到別人的答案，可以用瀏覽器 DevTools 檢查 WebSocket 訊息。
- 確認非 host 的 client 送出「公開答案」或判定事件時，server 會拒絕。
- 確認還沒全員送出答案時，「公開答案」會被拒絕。
- 確認結算畫面的一致題數和實際判定結果相符。
